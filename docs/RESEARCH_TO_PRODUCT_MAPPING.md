# Research v2.8 → Transit Application v2.0 Mapping

This documents **adopted mechanisms**, not evidence that a different AI team independently verified a product. Parent: [research-paper-workflow](https://github.com/ryotamatsuki/research-paper-workflow).

| Theory-paper control | Application analogue | Reason and key difference |
|---|---|---|
| Stage 0 phenomenon/idea | Stage 01 user problem | Human decision, understanding or experience with observable pain, not an economically novel theorem |
| Stage 1 source audit | Stage 02 data/license audit | Field coverage, actual retrieval, service dates, lawful use, not algebra |
| Stage 2 prior-art novelty kill | Stage 03 substitute-product kill | User task and decision outputs, not just feature labels |
| Stage 3 bounded candidate search | Stage 01/04 candidate register | Structural dedup + finite search budget, no artificial quota |
| Stage 4 minimal solved model | Stage 05 minimum real-data prototype | Profile-specific verifiable cases: decision, analysis or visualization; not a mandatory routing algorithm |
| Stage 4A independent attack | Stage 06 independent reference oracle | Different logic, real timetables and boundary violations; not AI model name |
| Stage 6 novelty re-kill | Stage 07 implementation-level re-kill | Confirm differentiation after feature reality, not idea deck |
| Stage 7 portability / falsification | Stage 07 scenario/data/user robustness | Baseline task comparison, OD contribution, coverage-limited claims |
| Stage 8 theory freeze | Stage 08 core logic/data contract freeze | UI can evolve under change control; no theorem certificate |
| Stage 9/10 build | Stage 09 fully integrated application | Versioned product repo, CI, deployment, live site |
| Stage 11 hostile referee | Stage 11 independent reviewer / public-site attack | Reproduction from judge-facing package; no fake independent pass |
| Stage 12 journal fit | Stage 00/11/12 competition eligibility / fit | Official published judging dimensions vs journal prestige |
| Stages 13–15 manuscript/submission | Stage 10–12 UX, release QA and submission freeze | Portal receipt, public link, licensing and post-deadline change control |

Non-transfers: global Nash equilibrium, formal proof-assistant gates, journal candidate completeness, referee proof exposition rules. Optional mathematical certification can be project-specific if an algorithm requires it; there is no universal Lean requirement.

## v2.0 product-specific additions

Early user screening before selection, experiments on the biggest unresolved assumption, matched baseline tasks, OD contribution comparisons, task-level build/UX iterations, operations rehearsals and machine-readable evidence dependencies are product-development controls. They do not require novel mathematics or impose feature quotas. READY is a pre-submission state; receipt checks apply only after submission.
